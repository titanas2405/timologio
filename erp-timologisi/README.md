# ERP Τιμολόγησης (σκελετός)

Web εφαρμογή (SaaS) τιμολόγησης με σχεδιασμό έτοιμο για διαβίβαση στο myDATA της ΑΑΔΕ.
Στοίβα: Node.js 22+, TypeScript, Fastify, Drizzle ORM, SQLite (ανάπτυξη).

## Εκκίνηση

```bash
npm install
npm run db:push     # δημιουργεί τη βάση dev.db
npm test            # όλα τα τεστ
npm run dev         # ανάπτυξη: εφαρμογή στο http://localhost:5173 (το /api πάει στον server, θύρα 3000)
```

Παραγωγή / δοκιμή σε έναν server:

```bash
npm run build       # χτίζει το frontend στο dist/web
npm start           # εφαρμογή + API στο http://localhost:3000
```

### Μεταβλητές περιβάλλοντος (.env)

- `DATABASE_URL`, `PORT`
- `APP_SECRET`: κλειδί 32 bytes (64 χαρακτήρες hex) για την κρυπτογράφηση των κωδικών που αποθηκεύονται
  (μητρώο ΑΑΔΕ, Viva). Δημιουργία: `node -e 'console.log(require("crypto").randomBytes(32).toString("hex"))'`.
  **Αν χαθεί, οι αποθηκευμένοι κωδικοί δεν διαβάζονται** και πρέπει να ξαναδοθούν. Σε παραγωγή φυλάσσεται εκτός κώδικα.

### Ενημέρωση υπάρχουσας βάσης

Για **νέα** βάση αρκεί το `npm run db:push`. Για βάση που **έχει ήδη δεδομένα** και φτιάχτηκε πριν την αποθήκη,
εφαρμόστε τα αρχεία του `migrations/` με τη σειρά (π.χ. `sqlite3 dev.db < migrations/0001_stock.sql`).
Μην τρέξετε `db:push` πάνω της πριν από αυτό: για την αλλαγή της αποθήκης το drizzle-kit προτείνει `delete from items`.

## Δομή

- `src/` backend (Fastify). Όλες οι διαδρομές του API είναι κάτω από το `/api`.
- `src/domain/` κανόνες (ΦΠΑ, τύποι παραστατικών, τρόποι πληρωμής, σύνολα). Τα χρησιμοποιεί **και** το frontend,
  ώστε τα σύνολα που βλέπει ο χρήστης να είναι ακριβώς αυτά που αποθηκεύονται.
- `src/routes/` ανεξάρτητα modules: προμηθευτές, αναζήτηση ΑΦΜ (`src/registry/`: μητρώο ΑΑΔΕ RgWsPublic2 ή VIES),
  πληρωμές με κάρτα (`src/payments/`: διεπαφή τερματικού και υλοποίηση Viva Cloud Terminal για SoftPOS).
- `src/crypto.ts` κρυπτογράφηση (AES-256-GCM) των κωδικών εξωτερικών υπηρεσιών.
- `web/` frontend (React + Vite): Αρχική, Παραστατικά (τιμολόγια, δελτία αποστολής), προβολή/εκτύπωση με λογότυπο,
  Πελάτες, Προμηθευτές, Είδη, Αποθήκη, Εισπράξεις & Πληρωμές, Αναφορές, Ρυθμίσεις.

## Τι υπάρχει ήδη

- Πολλοί οργανισμοί (multi-tenant): κάθε αίτημα στέλνει την κεφαλίδα `x-org-id`. Προσωρινό, θα αντικατασταθεί από σύνδεση χρηστών.
- Πελάτες, είδη/υπηρεσίες, σειρές παραστατικών.
- Πρόχειρο παραστατικό → **έκδοση** με συνεχή αρίθμηση ανά σειρά (σε μία συναλλαγή, χωρίς κενά).
- Ένα εκδομένο παραστατικό δεν τροποποιείται ποτέ.
- Υπολογισμός ΦΠΑ ανά γραμμή, ποσά σε λεπτά.
- Εισπράξεις & πληρωμές (`src/routes/cash.ts`): μια είσπραξη εξοφλεί ένα ή περισσότερα τιμολόγια (αυτόματα τα παλαιότερα
  ή όπως ορίσει ο χρήστης), το υπόλοιπο μένει «έναντι». Υπόλοιπα και καρτέλα πελάτη (τιμολόγια − πιστωτικά − εισπράξεις).
  Πληρωμές σε προμηθευτή ή σε τρίτο χωρίς καρτέλα. Μια εγκεκριμένη χρέωση κάρτας γίνεται αυτόματα είσπραξη.
  Οι εισπράξεις δεν διαβιβάζονται στο myDATA: είναι εσωτερική καταγραφή της κίνησης χρημάτων.
  Τρόποι πληρωμής με «Εξοφλείται με την έκδοση» (προεπιλογή: Μετρητά) γράφουν αυτόματα είσπραξη όταν εκδοθεί το τιμολόγιο.
  Μετρητά πάνω από 500 € (`CASH_LIMIT_CENTS` στο `src/domain/payment-methods.ts`· επιβεβαιώστε το όριο): ρύθμιση ανά οργανισμό
  «προειδοποίηση / επιβεβαίωση / απαγόρευση». Η απαγόρευση ελέγχεται και στον server (έκδοση, εισπράξεις, πληρωμές).
- Κωδικοποίηση (`src/routes/codes.ts`): πελάτες, προμηθευτές και είδη, ξεχωριστά αυτόματα (πρόθεμα + αύξων) ή χειροκίνητα.
  Μοναδικοί ανά οργανισμό· απόδοση κωδικών σε παλιές εγγραφές· barcode στα είδη· ο κωδικός «παγώνει» στο εκδομένο παραστατικό.
- Αναφορές: σύνοψη πωλήσεων, ημερολόγιο πωλήσεων (ΦΠΑ ανά συντελεστή, σύνολα ημέρας, εκτύπωση A4 οριζόντια, CSV)
  και είδη ανά πελάτη / πελάτες ανά είδος (με τα παραστατικά). Οι γραμμές χωρίς είδος ομαδοποιούνται με την περιγραφή.
  Ενηλικίωση υπολοίπων πελατών (0–30 / 31–60 / 61–90 / 90+ ημέρες από την έκδοση) σε οποιαδήποτε ημερομηνία αναφοράς.
  Για προμηθευτές χρειάζονται πρώτα τιμολόγια αγορών (`src/domain/aging.ts` είναι ήδη γενικό ανά αντισυμβαλλόμενο).
- Ένας προμηθευτής ανά είδος (+ κωδικός του είδους στον προμηθευτή): προτείνεται στις παραλαβές· η τελευταία τιμή αγοράς βγαίνει από τις παραλαβές.
- Ιστορικό τιμών στη γραμμή τιμολογίου (🕘 ή F4): τιμές στον πελάτη και σε όλους, τιμή αγοράς, περιθώριο· πρόταση τελευταίας τιμής πελάτη (ρύθμιση).
- Δύο τιμές ανά είδος: χονδρική (χωρίς ΦΠΑ) και λιανική (με ΦΠΑ). Διακόπτης «Τιμές με/χωρίς ΦΠΑ» σε κάθε παραστατικό (προεπιλογή στις Ρυθμίσεις):
  με ΦΠΑ το σύνολο γραμμής βγαίνει ακριβώς όπως γράφτηκε και ο ΦΠΑ υπολογίζεται από μέσα (`src/domain/totals.ts`).
- Έκπτωση % ανά γραμμή: η καθαρή αξία γραμμής (και ό,τι πάει στο myDATA) είναι μετά την έκπτωση· στα σύνολα «Αξία προ έκπτωσης» και «Έκπτωση».
- Ουρά (`mydata_submissions`) και worker (`src/mydata/worker.ts`) με επαναπροσπάθειες. Η πραγματική σύνδεση με την ΑΑΔΕ γράφεται στο `src/mydata/adapter.ts` (προς το παρόν υπάρχει μόνο η διεπαφή).

## Παράδειγμα χρήσης

```bash
# 1. Οργανισμός
curl -X POST localhost:3000/api/organizations -H 'content-type: application/json' \
  -d '{"name":"Η εταιρεία μου","vatNumber":"123456789"}'
# -> κράτα το id και βάλ' το στο x-org-id

# 2. Πελάτης και σειρά
curl -X POST localhost:3000/api/customers -H 'x-org-id: <ID>' -H 'content-type: application/json' \
  -d '{"name":"Πελάτης Α","vatNumber":"987654321"}'
curl -X POST localhost:3000/api/series -H 'x-org-id: <ID>' -H 'content-type: application/json' \
  -d '{"code":"Α","docType":"1.1"}'

# 3. Πρόχειρο τιμολόγιο και έκδοση
curl -X POST localhost:3000/api/invoices -H 'x-org-id: <ID>' -H 'content-type: application/json' \
  -d '{"customerId":"<CUSTOMER>","seriesId":"<SERIES>","lines":[{"description":"Υπηρεσία","quantity":1,"unitPriceCents":10000,"vatCategory":1}]}'
curl -X POST localhost:3000/api/invoices/<INVOICE>/issue -H 'x-org-id: <ID>'
```

## Τι λείπει (επόμενα βήματα)

1. Σύνδεση χρηστών (login) και ρόλοι.
2. Frontend: οι οθόνες με την ένδειξη «Σύντομα» (πιστωτικά, προσφορές, εισπράξεις).
3. PDF τιμολογίου στον server (τώρα: Εκτύπωση / Αποθήκευση ως PDF από τον browser).
4. Πιστωτικά τιμολόγια (τύπος 5.1 με συσχέτιση).
5. Σύνδεση myDATA: μετατροπή σε XML, κλήση `SendInvoices` στο dev περιβάλλον, αποθήκευση ΜΑΡΚ.
6. Μετάβαση σε PostgreSQL για παραγωγή (το schema ξαναγράφεται με `drizzle-orm/pg-core`).

## Προσοχή

- **Viva SoftPOS**: τα endpoints προέρχονται από την τεκμηρίωση του Cloud Terminal API (ECR) όπως την αποτυπώνουν SDK τρίτων.
  Δεν έχουν δοκιμαστεί με πραγματικό λογαριασμό. Δοκιμάστε πρώτα στο περιβάλλον Demo. Η διασύνδεση POS–ERP για το myDATA
  (υπογραφή παρόχου στο παραστατικό) δεν έχει υλοποιηθεί ακόμα.
- **Μητρώο ΑΑΔΕ (RgWsPublic2)**: η μορφή αιτήματος/απάντησης ελέγχθηκε με δείγματα, όχι με πραγματικούς κωδικούς.
- **Χαρακτηρισμοί εσόδων** (`src/domain/classification.ts`): η κατηγορία ορίζεται στο είδος (εμπόρευμα/προϊόν/υπηρεσία),
  ο τύπος Ε3 βγαίνει από τον πελάτη (με ΑΦΜ → χονδρική, ιδιώτης → λιανική, ΕΕ, τρίτες χώρες) και «παγώνει» στην έκδοση.
  Οι κωδικοί και οι επιτρεπτοί συνδυασμοί πρέπει να επιβεβαιωθούν με τους πίνακες της ΑΑΔΕ.
- **Δελτία αποστολής**: οι κωδικοί σκοπού διακίνησης (`src/domain/movement.ts`) και οι ημερομηνίες υποχρέωσης της Β' φάσης
  πρέπει να επιβεβαιωθούν με την τελευταία ανακοίνωση και τεχνική περιγραφή της ΑΑΔΕ.

Οι κατηγορίες ΦΠΑ (`src/domain/vat.ts`) και οι τύποι παραστατικών (`src/domain/doc-types.ts`) είναι οι συνηθισμένες.
Επιβεβαίωσέ τες με την τελευταία επίσημη τεχνική περιγραφή της ΑΑΔΕ πριν βγεις σε παραγωγή.
